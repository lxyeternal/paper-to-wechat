# 会议报告工作流：现场照片 → 公众号草稿箱

输入：一个装着现场幻灯片照片的目录（手机拍的即可）+ 报告人/会议信息。
输出：公众号草稿箱中一篇听会笔记。

和 `PAPER_WORKFLOW.md` 的关系：**排版、封面、发布、去 AI 味、术语规范、深度要求这些全部复用**，
差异只在"素材是照片不是 PDF""内容是一场报告不是一篇论文"。下面只写差异部分，
没写到的一律按 PAPER_WORKFLOW 执行。

## 和论文解读的三个根本差异

1. **一场报告 = 一串研究，不是一个研究**。报告人会把自己团队近几年的工作串成一条线，
   所以文章的骨架是"他为什么这么串"，而不是"这个方法怎么实现"。
2. **没有原文可查，只有照片**。拍不到的、被人头挡住的、听漏的，就不要写。
   宁可少写一个点，也不要靠推测补全幻灯片上没有的内容。
3. **读者要的是"前沿在往哪走"**。会议报告的价值在于它给出了一个领域的最新地图和判断，
   所以「启发与点评」的比重要比论文解读更大。

## 步骤

### 0. 查重（同 PAPER_WORKFLOW §0）

同一场报告、同一个团队的工作可能已经推过单篇论文解读。查重范围要同时覆盖 `papers/` 和 `talks/`：

- `grep -rliE "<报告人>|<系统名>|<会议名>" papers/*/article.md talks/*/article.md`
- 命中不一定要跳过：**报告里提到的某篇论文此前单独解读过，是加分项**，
  应该在正文里明确串联（"本账号此前单独解读过《…》"），这正是账号做成系列的价值。
  真正要避免的是同一场报告被写两遍。

### 1. 建目录

- slug 规则：`talks/YYYY-MM-<会议简称>-<报告人拼音>`（如 `talks/2026-08-ccf-nss-xuke`）
- **原始照片不入库**（一场报告二十几张 4K 照片就是几十 MB），只留裁好的配图。
  在目录下写一个 `SOURCE.txt` 记下原始照片的位置和拍摄时间，方便日后重裁。

### 2. 裁图（这一步决定文章能不能看）

会场照片直接发公众号是没法看的：一半画面是天花板和后脑勺，幻灯片是斜的、暗的、带反光。

- `.venv/bin/python scripts/crop_slides.py <照片目录> talks/<slug>/assets/slides`
- 脚本按亮度找投影屏边界（会场暗、屏幕亮），允许中间有小缺口，所以前排观众的头
  不会把裁切框切断；幻灯片深色标题条会被亮度阈值切掉，脚本会自动往上多留一截。
- 同时压到 1800px 宽、1MB 以内（**公众号正文图上限就是 1MB**，不压会传失败）。
- 裁完**逐张 Read 检查**，标准同 PAPER_WORKFLOW §3 的图表完整性检查，外加两条：
  - **标题行完整**：幻灯片标题是这张图的索引，被切掉图注就没法写；
  - **关键数字没被人头挡住**：底部三分之一最容易被遮，挡住了就换一张同内容的照片。
- 裁得不对时的调参：标题被切 → 调大 `top_pad`；框太小只裁到半边 → 调小 `col_t`/`row_t`。

### 3. 选图（宁缺毋滥）

一场报告拍二十几张，**只选 8 到 12 张**。选取标准按优先级：

1. 全景/框架图（读者的地图，必选）
2. 核心科学问题那一页（报告的题眼，必选）
3. 你准备深挖的 2-3 个点各配一张
4. 防御体系/方法总图
5. 有硬战果的那几页（CVE 编号、录用会议、上线系统）
6. 前瞻方向一张，总结一张（二选一即可，别都放）

不选：纯文字大纲页、致谢页、和主线无关的宣传页、拍糊的。

图片按 `assets/slide-NN-<语义名>.jpg` 命名，编号即正文出现顺序。

### 4. 写文稿

front matter 用 `kind: talk`（靛蓝强调色 + 封面"现场报告"标签），其余字段同论文解读。
`venue` 填会议简称加年份，`title_en` 位置改填"<会议全称> · <报告人>特邀报告"（封面副标题会用它）。

结构骨架（按报告本身的推进顺序走，别自己重排）：

| 节 | 写什么 |
|---|---|
| TALK INFO｜报告信息 | 报告人、单位、会议、时间、主题；一句话说明这是听会笔记、图为现场拍摄 |
| OVERVIEW｜导读 | 这场报告换了什么视角看问题，比复述结论重要 |
| LANDSCAPE｜地图 | 全景框架图 + 它揭示了什么结构 |
| CASES｜真实案例 | 报告举的事故，挑 2 个从本账号的领域视角重讲 |
| QUESTION｜科学问题 | 报告收束出的那个统一判断，用引用块 `> ` 拎出来 |
| RISKS｜深挖 | **2-3 个最有信息量的风险，每个讲透机制、实验设计、所以呢** |
| DEFENSE｜防御 | 防御体系图 + 它的设计取向说明了什么 |
| WORKS｜落地 | 挑 3 个和账号主线最相关的系统，带硬战果 |
| FUTURE｜前瞻 | 还在路上的方向，诚实说明"能不能成还不好说" |
| TAKEAWAYS｜启发与点评 | 对研究者 / 对从业者 / 一句系列串联的观察 |

深度要求完全照搬 PAPER_WORKFLOW §4 的六条。对报告类另有三条：

- **讲清实验设计为什么成立**。报告里一闪而过的对照实验（零假设、跨模型复现）
  往往是最值得展开的，读者在现场听不出门道，文章要替他讲明白。
- **保留报告人的原话逻辑**。核心判断用引用块原样给出，不要改写成自己的话再"总结"。
- **不确定就标不确定**。照片没拍全的数字、听不清的名字，要么不写，要么写"现场给的是…"，
  不要替报告人把话说满。

### 5-6. 封面、排版、发布

同 PAPER_WORKFLOW §5/§6，`--kind talk`，脚本参数里的路径换成 `talks/<slug>`。

封面不走论文那套深蓝满版底，改成白卡浮在浅色底上，目的是让读者在列表里一眼分出会议报告和论文解读：

- `--kind talk` 自动套用 `templates/cover_talk.html`（A 版·冷灰蓝底 + 26px 圆角白卡 + 左侧竖排靛蓝标签条 + 右上角叠层幻灯片装饰）。
- 备选 `templates/cover_talk_b.html`（B 版·米白纸感 + 横线纸纹 + 同款竖排标签条），用 `--template` 指定。
- 两版共用同一套设计语言：26px 卡片圆角、78px 竖排标签条（顶部一个带光晕的白点 + 竖排类型词）、胶囊形会议徽章、三层叠加阴影、46px 圆角小色条作为标题下的引导。差别只在冷灰蓝与米白两套底色。
  标题一行或两行都排得住（A 版 45px 双行封顶，B 版 46px），改版式时用一长一短两个标题各渲一次再定。
换封面重发：清掉 `publish.json` 里的 `thumb_media_id`（保留 `draft_media_id`）再跑发布，会原地更新草稿。

## 常见坑

- **配图超过 1MB 传不上去**：`crop_slides.py` 已自动压，但如果手工替换过图要自己确认。
- **人名听错**：现场只听音很容易写错字（徐恪 / 徐克）。优先从幻灯片脚注的作者列表、
  论文引用行里核对写法，拿不准就问用户。
- **把报告人团队的工作写成"我们"**：报告是别人的工作，全程第三人称，
  只有"笔者在台下听"这类现场视角可以用第一人称。
- **幻灯片上的数字与已发表论文对不上**：以幻灯片为准并注明"现场给的是…"，
  两个数字都想给时说明口径差异，别默默换成论文里的数。
